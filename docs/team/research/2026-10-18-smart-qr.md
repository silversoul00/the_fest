## 1. Goal
One QR per ticket. A normal phone camera opens a plain web page showing only the basics (fest, date, first name, ticket
type, valid / used / cancelled). THE FEST scanner reads the same QR and, **even with no internet**, opens extra sealed
details, but only the ones for that scanner's job: gate, lunch, stay, first aid, organizer. When online it also shows the
live status from the server. The ticket screen can show a "live" QR that changes every 30 s, so an old screenshot is flagged.

## 3. Findings
- Prior art: Denso Wave **SQRC** already stores public + private data in one QR; private part readable only by a reader
  holding the key. So "public + private QR" alone is not new. [SATO SQRC](https://satoasiapacific.com/solution/security-qr/)
- Prior art: US patents on **multi-level security QR** (public codebook + several private codebooks by classification;
  codebook URLs fetched over network; a later one titled "dynamic multi-level security"). Attorney must read these.
  [US 12307325](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/12307325),
  [US 12682196](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/12682196) (text not readable by me — uncertain scope)
- Prior art: Ticketmaster **SafeTix** rotates a barcode every 15 s with TOTP from per-event + per-customer keys; verified
  server-side; it was reverse-engineered because secrets were in console logs.
  [Gigazine](https://gigazine.net/gsc_news/en/20240710-ticketmaster-safetix-ticket)
- URL `#fragment` is not sent to the server in HTTP requests (RFC 3986 behaviour; MDN page could not be fetched —
  https://developer.mozilla.org/en-US/docs/Web/URI/Reference/Fragment was blocked). Page JavaScript **can** read it, so our
  public page must never read `location.hash`.
- QR size measured with the repo's own `qrcode` lib (random base64url URLs, EC level M): 140 chars → v8 (49 modules),
  200 → v10, 250 → v11, **300 → v13 (69 modules)**, 350 → v14. Today's TF1 payload (137 chars) is ~v8.
- India: s.3(k) bars "computer programme per se"/algorithms/business methods; CRI Guidelines 2025 accept a "technical
  effect", e.g. "security enhancement in computer networks/systems". [AIPPI](https://www.aippi.org/news/decoding-cri-guidelines-2025/)
- India: provisional e-filing ₹1,600 for natural person/startup; complete spec within **12 months, no extension**; prior
  public disclosure (posts, pitch without NDA, product listing) can destroy novelty; grace only for notified exhibitions /
  learned societies. [Intepat](https://www.intepat.com/blog/patent/provisional-patent-application/)
- DPDP Rules notified 14 Nov 2025; notice, security, retention and **child (under-18) verifiable parental consent**
  rules apply 18 months later (~May 2027). [Storyboard18](https://www.storyboard18.com/digital/breaking-govt-notifies-final-dpdp-rules-sets-staggered-rollout-with-key-obligations-for-data-fiduciaries-84201.htm)
- Code facts: scanning is online-only today (`Scanner.tsx` says "No connection"); `sw.js` never caches pages; counter comes
  from `counterFor(duty)` (gate/lunch/stay); `/api/scan` rejects payloads > 400 chars; ticket QR rendered server-side in
  `tickets/[id]/page.tsx` with `signTicket()`; e2e feeds a QR image (`tests/run-e2e.sh` lines 33–34).

## 4. Recommendation

### 4.1 Format "TF2" (one QR = one URL)
`https://thefest.in/t/<P>#<F>[.<L>]` (host = `NEXT_PUBLIC_SITE_URL`; the scanner ignores the host, it checks the signature).

| Part | Bytes (before base64url) | Seen by server? |
|---|---|---|
| **P** = `0x02` · ticketId(16) · keyEpoch(1) · pathTag(6) | 24 → 32 chars | yes (public page) |
| **F** = nonce(12) · sections · ECDSA sig(64) | ~150–190 | **no** |
| **L** = live code (4) — only on the live ticket screen | 6 chars | no |

- **pathTag** = first 6 bytes of HMAC-SHA256(k_path, ticketId‖epoch). Public page rejects anything without it → ticket IDs
  seen elsewhere (old TF1 QRs, `/tickets/<id>` URLs) can't be used to open the page; random guessing is hopeless (UUID + 48 bits).
- **Signature**: existing ECDSA P-256/SHA-256 key (`TICKET_PRIVATE_KEY`), IEEE-P1363, over `"TF2"‖P‖nonce‖sections`.
  Scanner verifies **before** decrypting (WebCrypto ECDSA verify uses the same raw 64-byte format). Volunteers sharing a role
  key therefore still cannot forge or edit sections.
- **Section** = role(1) · len(1) · AES-256-GCM ciphertext+tag. One random nonce per QR render, shared by all sections —
  safe because every section uses a different key. AAD = P. **Tag 4 bytes** (WebCrypto `tagLength: 32`): integrity comes
  from the ECDSA signature; the tag is only a "this key fits" check (wrong-key false match 1 in 4 billion). This is what keeps
  the QR ≤ 300 chars. Sections that would be empty are left out.
- **Contents (short codes, not prose):**
  - gate: liveSecret(8) · full name (≤20 bytes UTF-8) · `0x1F` · ticket type label (≤12)
  - lunch: lunch-day bitmask relative to fest `starts_on` (1 byte; 2 if fest > 8 days)
  - stay: flags (1 byte, bit0 = stay)
  - aid (only if student opted in): blood group code (1) · emergency phone 10 digits packed BCD (5) · allergies (≤16 bytes)
  - org: holder phone BCD (5)
- **Size**: typical (gate+lunch+org) ≈ 265 chars; worst case (all five + live code) ≈ 295 chars → QR v13-M. Builder must
  assert in a test that the worst case ≤ 300 chars and QR version ≤ 13; truncate name/allergies to fit, never grow.
- **Keys** (no new env var, no DB key table): `master = HKDF-SHA256(ikm = TICKET_PRIVATE_KEY's private scalar, info "tf2-master")`
  (optional override env `QR_SEAL_MASTER`). Then `k_role = HKDF(master, salt = festId, info = "seal|<role>|<epoch>")`,
  `k_path = HKDF(master, info "path")`, `liveSecret = HMAC(master, "live"‖ticketId)[0..8]`.
- Each render (page load) re-seals from current DB data, so new add-ons appear on the next ticket open.

### 4.2 Keys to scanner phones, rotation, lost phone
- New `GET /api/scan/keys?festId=` (scanner session + `scannableFests`, `Cache-Control: no-store`) returns: fest start/end
  dates, `epoch`, keys for **current and previous epoch** for the roles this person may use, and the public key (JWK).
  Roles: volunteer → only the role from `counterFor(duty)` (add `aid` for duty starting "first aid"/"medical"); owner and
  co-organizers → all five.
- Scanner imports keys as **non-extractable** CryptoKeys, keeps them in IndexedDB with expiry = min(session expiry, fest end
  + 1 day); wipes them on Lock/logout and on a 401. Refetch on page load and every 10 min while online. Keys are not served
  after fest end + 1 day.
- **Lost phone**: Volunteers tab → "Phone lost? Reset scanner keys" (owner/co-organizer): `fests.qr_epoch += 1` and delete
  `sessions` with `kind='scanner'` for that fest's staff (everyone logs in again — they already must). New ticket opens
  seal under the new epoch; honest scanners still read previous-epoch QRs (those keys are already exposed anyway); QRs two
  epochs old show "Can't read offline — needs network". Also remove the volunteer from the fest as today.
- Offline only works if the scanner page **stays open** (pages aren't cached and login is always re-asked). Show "Offline
  ready — keep this page open" when keys are cached.

### 4.3 Scanner flow (`Scanner.tsx`)
1. Decode text. `TF1.` → legacy path (below). `…/t/<P>#<F>` → TF2. Anything else → "Not a THE FEST ticket".
2. TF2: verify signature locally → fail = red "Fake or tampered". Open the sections this phone has keys for. Gate section
   won't open with this fest's keys → "Not a ticket for this fest" (or "needs network" if epoch is too old).
3. Show the role card: **Gate** name + type + live chip; **Lunch** "Lunch today ✓/✕ (day x of y)"; **Stay** yes/no;
   **First aid** blood group, allergies, tap-to-call emergency number (read-only, nothing redeemed); **Organizer** all of
   that + holder phone. A volunteer's screen/DOM must never contain another role's data.
4. Online → POST `/api/scan` as now (send the full text); the server verdict replaces the local one ("live status").
   Offline → local per-device dedupe (IndexedDB, key ticketId+slot), amber "Offline ✓ — saved, will sync", push to a queue;
   on `online` replay the queue to `/api/scan`; any server "duplicate" is shown in the feed as "Synced: was already used at …".
5. **Live chip**: with L present, compute `HMAC-SHA256(liveSecret, floor(unix/30))[0..4]` for steps −2…+1 → "Live ✓";
   wrong/old → "Old screenshot"; no L → "Static (print/screenshot)". v1 = **warning only**; single-use at the gate already
   stops double entry when online.
- Legacy **TF1**: unchanged online path. Offline: verify the signature with the public key, gate-only local dedupe, card says
  "Old-style ticket — no sealed details". Backup code TF-XXXX-XXXX unchanged (online only).

### 4.4 Server (`src/lib/scan.ts`, `/api/scan`)
- `resolveTicket` accepts TF1 and TF2 (verify sig + pathTag server-side; fest check via the ticket row). Payload cap 400 → 600.
- Verdict gets `live: 'live' | 'stale' | 'static' | null` (server recomputes from liveSecret).
- Counter `aid`: status only (valid/used/void), never redeems, never returns medical data (medical data travels only sealed).
- `counterFor`: `first aid…`/`medical…` → `aid`. Organizer duty picker gets "First aid".

### 4.5 Public page `/t/[p]` (server component, no client JS that reads the hash)
- Decode P; any failure (bad length/version/pathTag/no ticket) → the **same** generic "Not a valid THE FEST ticket" 404.
- Shows: fest name, dates, college + city, ticket type, holder **first word of name** (≤20 chars), badge "Valid" / "Used"
  (no time, no gate) / "Cancelled", "Verified by THE FEST", and "This is your ticket? Open it in THE FEST" link. Nothing else
  (no email, phone, code, order, lunch/stay, perks).
- Headers: `robots: noindex`, `Cache-Control: private, no-store`, `Referrer-Policy: no-referrer`; `robots.txt` Disallow `/t/`.

### 4.6 Ticket screen (`tickets/[id]`) + offline ticket
- Server builds the TF2 URL; a small client `LiveQR` gets `{url, liveSecret}` and redraws every 30 s with a countdown ring
  (browser `qrcode`). "Static QR (for print)" toggle shows the URL without L. Backup code stays.
- Save `{fest, type, date, url, liveSecret}` in localStorage; `/offline` lists saved tickets and draws the live QR, so a
  student without signal at the venue can still show it. Clear on logout. Builder: make sure `/offline`'s JS chunk is cached
  (visit/prefetch it from the ticket page) — risk, test it.

### 4.7 First-aid card (opt-in)
- Table `medical_profiles(user_id pk → users on delete cascade, blood_group text check (A+…O−, unknown), allergies
  varchar(24), emergency_phone char(10) check digits, consent_version text, consented_at timestamptz)`, RLS enabled like the rest.
- `/me` → "First-aid card (optional)": blood group, allergies, emergency phone, two ticks: consent + "I am 18 or older"
  (no 18+ tick → can't save). "Delete my first-aid card" button removes the row.
- Who sees: only first-aid-duty volunteers and the fest's owner/co-organizers, by scanning. Not on the public page, ticket
  page (owner sees own card on /me only), CSV, analytics, API responses, logs.
- Consent wording (draft for lawyer): *"Share my first-aid card with the first-aid desk at fests I attend. THE FEST hides my
  blood group, allergies and emergency number inside my ticket QR. Only volunteers on first-aid duty and that fest's
  organizers can open it, by scanning my ticket with THE FEST scanner, even without internet. Gate, lunch and stay
  volunteers can't see it and it is not on the public ticket page. I can delete it here any time; new QR codes will then leave
  it out, but a screenshot or print I made earlier can still be opened by that fest's first-aid desk until the fest ends."*
- Schema v2.4: `alter table fests add column if not exists qr_epoch smallint not null default 1;` + `medical_profiles`.
  Apply to production only with Harshith's say-so (as before).

## 5. Acceptance criteria
1. New tickets show a TF2 QR; phone camera / any QR app opens `/t/…` showing fest, dates, type, first name, status, nothing more.
2. Public page HTML contains no full name, email, phone, ticket code, perks or medical data; it has noindex, no-store, no-referrer.
3. `/t/` with a random string, a real ticketId with wrong/missing pathTag, or a void ticket's id with tampered tag → identical
   generic 404 (same status and body).
4. Changing any byte of P or F → scanner shows "Fake or tampered" (online and offline).
5. Worst-case QR (all sections + live code, 20-char name, 16-byte allergies) ≤ 300 chars and QR version ≤ 13; scans in the e2e
   fake camera.
6. Gate volunteer offline: sees full name + type; lunch volunteer offline: only lunch today yes/no; stay: only stay; their
   pages never contain blood group/phone (assert on DOM text).
7. First-aid volunteer offline sees blood group, allergies and the emergency number as a tap-to-call link; nothing is redeemed.
8. Organizer/co-organizer sees all sections incl. holder phone.
9. `/api/scan/keys` → 401 without scanner session; 403 for someone not on the fest; a gate volunteer's response has only the
   gate key; keys not served after fest end + 1 day.
10. TF1 QRs printed before this change still admit online exactly once; backup codes still work.
11. Offline gate scan → amber "saved"; same ticket again on that phone → "Already in (this phone)"; back online → queue syncs;
    a ticket already admitted at another gate shows "Synced: was already used". Ticket is never admitted twice in the DB.
12. Lunch offline on a non-lunch day → "No lunch today"; once synced, perk_redemptions has one row per day max.
13. Live QR changes every 30 s; a code older than ~90 s → "Old screenshot"; static QR → "Static" chip; both still admit once online.
14. "Reset scanner keys" bumps epoch, logs out that fest's scanners; QRs from the previous epoch still open after re-login;
    two epochs old → "needs network". Only owner/co-organizers can press it.
15. First-aid card can't be saved without both ticks; deleting it removes the row and the next QR has no aid section; no
    medical data in CSV export, analytics, logs (`app_errors`), or any API JSON.
16. Saved ticket shows on `/offline` with network off; cleared after logout.
17. 390px: public page, ticket screen (QR ≥ 260px wide, countdown visible), every scanner role card and the first-aid form fit
    without horizontal scroll.
18. Money unaffected: existing `money.py`, `refunds.py`, `race.py` and the full `run-e2e.sh` pass.
